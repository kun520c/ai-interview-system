public JudgeProvider judgeProvider(JudgeProperties settings, DeepSeekEvaluationClient deepSeek,
                                  ObjectProvider<JevClient> jev, ObjectProvider<JevProperties> properties,
                                  ObjectMapper mapper, LlmEvaluationValidator validator) {
    var fallback = new DeepSeekJudgeProvider(deepSeek);
    return switch (settings.getProvider()) {
        case DEEPSEEK -> fallback;
        case JEV -> new JevJudgeProvider(jev.getObject(), properties.getObject(),
                deepSeek, fallback, mapper, validator);
    };
}

switch 在启动时执行，创建一个供业务注入的 JudgeProvider。没有额外 Factory 框架、ServiceLoader 或运行时热切换机制。DeepSeek 默认被选中，Jev Client / Properties 仅在 ai.judge.provider=jev 时创建，避免默认启动也强制要求 Jev Key。

整个 JudgeConfiguration 还要求 deepseek.enabled=true。因为 Jev 正常路径要用 DeepSeek 生成文字，故障路径也要用它回退；选择 Jev 不代表可以关闭 DeepSeek。编排服务另要求 Milvus 和 DeepSeek 都启用，这个既有业务条件没有变。

这个机制如何被证明？

JudgeConfigurationTest 验证默认实现、显式 Jev、唯一 Judge Bean、按需创建以及无效配置启动失败；DeepSeekJudgeProviderTest 穿过真实原 Client 和 Mock HTTP，检查旧 Prompt、JSON、分数和元数据保留。它们没有访问在线模型。

Node 1：Client 与 Provider 为什么分开？

Client 回答“服务怎么调用、响应能否解析且完整对应这次请求”；Provider 回答“这个判断在本项目是否成立、怎样转成原评价格式”。协议可能变而评分规则不变，评分量表也可能变而 HTTP 不变，职责分开让修改和测试各自聚焦。

“一次”限定 evaluate 里 fallback 的调用次数。JevClient 没有 HTTP 重试；若生成阶段失败，DeepSeek 已尝试一次写反馈，再尝试一次完整 Judge，因此可能有两次 DeepSeek 请求。总耗时和费用未在线验证，不能凭“双模型”宣称更快或更便宜。未来 Workflow 的合法重试是另一次评价尝试，不是本方法内部无限重试。

fallback 接收同一个 context 和原 prompt，发生在 Judge 内部；不重跑 RAG、不新建第二条 retrieval batch，也不在 Provider 内插入评价或推进状态。之后仍通过外层统一 Validator 和原持久化路径。

模型返回合法格式仍可能误判，而且它不知道最新 Session 状态、并发执行权和持久化约束。当前 Provider 没有 Mapper、事务或 CAS 权限；只能给建议。原 Java Policy 根据 MAIN / FOLLOW_UP 阶段、总分、CORE 覆盖和目标评分点决定 action，然后由原 Workflow 的短事务和 CAS 执行。
