# InnoDB 事务、工作单元与 ACID

## 从业务不变量确定边界

在 MySQL 8.0 的 InnoDB 中，事务把多步读写组织成一次提交。以礼品卡余额转移为例，同币种下两张卡的余额合计应保持不变，余额应非负，每笔转移只生成一条流水。扣减、增加和记流水是同一工作单元，执行时应确认两张卡都存在、扣减额度合法且每步得到预期结果。单纯对余额和流水各加约束，无法自动保证涉及多行的金额守恒。数据库检查已声明的约束，应用用正确的 SQL、锁定条件和事务边界维护其余不变量。这体现了 ACID 的一致性。

## 事务失败时应用需要做什么

InnoDB 的原子性允许同一事务里的扣款、入账和流水一起提交或回滚。连接使用 autocommit 时，独立的普通 DML 通常各自提交。写出三条相邻 SQL 仍可能出现扣减已经提交、入账却因记录不存在而未修改的结果。可以显式开启事务，由调用方在三步均通过时执行 COMMIT，在业务错误或不确定状态下结束该工作单元。InnoDB 有些错误仅回滚出错语句，例如默认的锁等待超时，后续直接 COMMIT 仍可能提交前序写入。部分 DDL 存在隐式提交，远程 HTTP 操作也无法靠本地 ROLLBACK 撤回。

## 隔离与持久各回答一个问题

InnoDB 隔离级别控制并发事务何时互相看见、何处需要锁。MySQL 8.0 的 REPEATABLE READ 与 READ COMMITTED 都可以进行普通一致性读，但前者通常沿用事务的首个读快照，后者每次一致性读取新快照。业务判断要依靠当前值时，可在合适事务中锁定读取，或将谓词放入条件更新并核对行数。持久性关心提交后的数据能否恢复。崩溃恢复可用 redo 重放变更，再用 undo 回滚未完成事务。具体保证依赖刷盘配置，例如 `innodb_flush_log_at_trx_commit`，也依赖 binlog 设置、操作系统和存储是否兑现刷盘，以及所讨论的故障类型。磁盘或整机故障还需要独立的备份与恢复策略。

## 可观察的工程例

在一次性测试库准备两张卡，让第二步更新指定不存在的卡。第一轮让每条 DML 自动提交，第二轮在一个显式事务中把第二步影响行数为零视为失败并 ROLLBACK。两轮都用新连接查余额和流水。由此可以观察部分提交与整体回滚的区别。并发正确性和提交后的耐久性需要分别设置读写交错和故障前提，普通查询对账无法模拟断电。
