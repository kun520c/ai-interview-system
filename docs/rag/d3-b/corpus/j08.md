# Stream 管线、顺序和并行归约

适用 Java SE 21 Stream API。这里的来源是有遇到顺序的常规 List。

## 延迟执行与副作用

filter、map、peek 是中间操作，返回管线供后续组合；count、toList 和 forEach 是终止操作。实现可以在不改变结果时省略遍历或中间阶段。对已知大小的 List，stream.peek(audit).count() 在 peek 不改变元素数时可直接使用已知大小，audit 并无必达保证。流函数应避免修改来源，通常应无状态，避免依赖执行中可能改变的外部值。即使本次 peek 被执行，也没有建立审计的可靠失败合同。

## 并行写入与顺序

parallelStream().forEach(resultArrayList::add) 会使多个任务共享修改普通 ArrayList，可能丢数据或破坏容器。并行 forEach 也不保证遇到顺序。forEachOrdered 在来源有顺序时按遇到顺序执行动作，单独处理它的业务失败语义仍由调用者负责。应把纯计算表示为 filter、map 后的 toList，由流实现归约并保留遇到顺序，然后由明确的步骤提交审计。toList 返回不可修改列表；可变结果需要适合的收集器或显式复制。

## 并行决策的成本

例如解析大量独立文本记录时，先用串行流获取输出，测量数据拆分粒度、每项计算量和顺序合并成本。可再用等价并行路径比较吞吐和尾延迟，观察是否竞争共享 CPU 或 I/O。小集合、不能良好拆分的输入、有序阻塞 I/O 均可能抵消并行收益。能证明满足原顺序合同且度量有改善时，再启用并行。
