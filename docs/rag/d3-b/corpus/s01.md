# Spring IoC、依赖注入与候选 Bean 解析

适用 Spring Framework 6.2.19，项目由 Spring Boot 3.5.16 管理版本。IoC 是将组件的创建、配置、组装和受管生命周期交给容器。容器读取 Bean 定义，知道怎样建立对象、怎样满足其依赖、何时执行初始化与销毁。DI 是落实 IoC 的方式。业务类声明自己需要的协作者，由容器从构造器、工厂方法参数或属性注入。对必需依赖使用构造器，可在创建时建立完整状态并将字段设为 `final`。受管类只有一个构造器时可以省略 `@Autowired`。可选属性可用 Setter 配置，并给缺省行为。业务类仍依赖协作者的行为合同，配置可以更换实现，单元测试可以直接给构造器传入替身。

## 单值候选与多值注入

假设邮件和短信都实现 `NotificationSender`，两者均为可自动注入的 Bean。单值参数 `NotificationSender sender` 按类型得到两个候选，在没有限定符、首选者、有效参数名等消歧规则时创建失败。将邮件实现标为 `@Primary` 可使它成为同一候选集合内的默认单值实现。给短信实现和专用消费者的参数使用相同的 `@Qualifier("sms")` 可先缩小候选集合，邮件的 `@Primary` 不会把被排除的实现带回来。限定符允许多个匹配项。它表示对类型候选的过滤，可以用 Bean 名称作为后备匹配值。6.2 的 `@Fallback` 可把候选声明为后备，若剩下唯一常规候选，单值注入可使用该实现。

另一个组件可以用 `List<NotificationSender>` 取得所有符合条件的实现，邮件的 `@Primary` 不会将列表压缩到一个元素。若列表有广播顺序要求，应显式定义并测试排序规则。参数名消歧依赖编译保留参数名等前提，改参数名也可能改变选择结果。对依赖的渠道属于业务要求的场景，显式限定符使意图可维护。可在小型上下文测试中依次验证默认邮件、指定短信和全渠道列表，并让两个无限定候选的测试明确观察创建失败。
