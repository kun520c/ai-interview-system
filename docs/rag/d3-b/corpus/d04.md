# 联合索引的定位、排序与过滤

## 键按字典序排列

以 MySQL 8.0 InnoDB 的设备事件表为例，二级索引 `(device_id, severity, created_at)` 先按设备排序，同设备下按级别排序，同级别内再按时间排序。条件 `device_id=7 AND severity='WARN' AND created_at>=?` 固定两列等值前缀，可在该前缀内从时间下界开始扫描连续区间。去掉级别条件后仍可定位设备 7 的前缀，但每个级别有自己的时间子区间，普通范围访问不能靠一段连续区间跳过每个级别里的旧记录。MySQL 有适用条件严格的 Skip Scan，可在某些索引覆盖和查询形态下枚举跳过的键部分，实际是否使用取决于代价和计划。

## 区分排序、过滤与覆盖

若所选路径沿该索引遍历，固定设备和级别时可利用索引提供 `ORDER BY created_at` 的顺序。跨多个级别时，事件先按级别成组，各组内部按时间排列，扫描顺序无法提供全局时间顺序。可以让优化器排序，或为重要查询评估 `(device_id, created_at)` 的额外写入成本。没有参与边界定位的谓词仍可过滤候选。InnoDB 二级索引上，满足条件的索引条件下推（ICP）可先用索引元组检查条件，减少之后的完整行访问。ICP 与覆盖处理的是两个不同问题。覆盖要求该索引能提供谓词、投影等所需列。新增只存在于聚簇记录的备注列后，当前二级索引通常需要取表行。

## 计划与验证

在同一测试数据上比较带和不带级别条件的查询，各运行一次只投影设备、级别、时间与一次额外投影长备注的版本。用 EXPLAIN 查看 `key`、`key_len` 和 `Extra`，必要时补 JSON/TREE 计划。 `Using filesort` 表示额外排序步骤，可能在内存完成。 `Using index` 常用于判断索引覆盖，`Using index condition` 反映 ICP。索引可以帮助定位，却仍可能需要排序或取表行。反过来，缺中间列也不代表这个索引毫无用途。比较时以真实选择性、实际读取与延迟为依据。
