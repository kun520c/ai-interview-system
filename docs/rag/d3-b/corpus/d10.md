# Redis 键过期、内存淘汰与未命中诊断

## 到期时间与内存压力分别起作用

Redis OSS 7.2 可以为键设 TTL，到期以后访问该键会发现它已过期，这称为被动过期。服务器也定期在设有过期时间的键中抽样并主动清理，键从逻辑上不可读和底层释放内存并不需要发生在同一瞬间。内存淘汰由 `maxmemory` 与策略触发，作用是让实例按配置腾出内存。若库存展示值设置 10 分钟 TTL，启用某个允许淘汰的策略后仍可能在第 2 分钟被逐出，TTL 只决定过期边界。业务主动 DEL、实例切换或启动时没有恢复缓存也可能导致未命中。

## 策略与候选空间

`allkeys-lru` 可从全部键中找候选，`volatile-lru` 只考虑设过期时间的键。Redis 用抽样近似 LRU，无法承诺精确选择全局最久未访问的键。设为 `noeviction` 时不会为腾出内存而淘汰；volatile 策略找不到合格候选时也可能无法释放内存。超过内存预算后，需新增内存的命令可能收到 OOM 错误，读取通常仍能继续。会话状态与纯缓存若共用实例，先明确能否提前逐出和内存写入失败时如何处理。

## 在实例层区分可能原因

如果某个商品缓存明显早于计划的 TTL 未命中，可以比对 `maxmemory`、淘汰策略、`INFO memory` 和两次 `INFO stats`。 `expired_keys` 的增量说明实例有过期活动，`evicted_keys` 的增量说明实例发生了内存淘汰。它们是聚合统计，无法单独证明哪一原因删除了该商品键。再结合相同时间范围内的应用删除或写入失败记录、实例角色和重启时间来缩小范围。缓存 miss 应从权威数据源读取，并根据热点、容量和 TTL 约定回填。

## 两个可区分的实验

在一次性 Redis 测试实例给一个键短 TTL，低内存压力下观察 TTL、GET 和过期计数变化。重置隔离实例后改为容量有限且可淘汰的策略，用足够多的缓存项造成压力，观察淘汰计数与写入返回值。不能要求近似策略每次都先删除同一个目标键。用两个场景分别验证过期和淘汰，避免只观察一次 GET miss 就归因。
