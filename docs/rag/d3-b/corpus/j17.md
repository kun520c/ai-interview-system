# 类加载、初始化、类型身份和 SPI

适用 JLS/JVMS SE 21 的普通类和接口，以及 Java SE 21 类加载 API。

## 加载、连接和初始化

加载依据二进制表示建立 Class。连接中的验证检查结构和字节码约束；准备创建静态字段并赋默认值，不执行 JVM 指令；带 ConstantValue 的静态字段在 JVM 初始化流程中取得常量值。解析把符号引用落实到对应类、字段或方法，可以延后。初始化执行类的静态字段初始化和静态代码块。读取 Config 声明的非常量 static int retries 首次触发 Config 初始化；读取 static final int PORT = 8080 不触发，因为它是由常量表达式初始化的基本类型常量变量。static final Integer 或通过方法计算的 final int 不属于此例。new Config() 可触发类初始化；同一定义类成功初始化后，再 new 运行实例构造但不重复静态代码块。

## 定义加载器与插件冲突

普通类或接口的运行时身份由二进制名称和定义加载器共同确定。两个加载器各定义一份 api.Payment 时，插件实现的一份接口不能强转为宿主持有的另一份。先比较宿主和插件使用的接口 Class 是否同一对象，再看定义加载器和代码来源，可配合 -Xlog:class+load 查找重复 API。默认 loadClass 先检查已加载，再委派父级，最后尝试本地查找；自定义加载器可以改变策略。发起加载器可以委派给最终的定义加载器。常见隔离方式是把公共接口交给共同父加载器，插件侧只持有实现和私有依赖。

## SPI 提供者可见性

ServiceLoader.load(Service.class) 通常用当前线程的上下文加载器查找，也可传入明确的加载器；使用具名模块时还需满足 uses/provides 和 provider 类或工厂方法的部署条件。提供者实例仍须满足宿主所用的 service 类型。换一个能看到插件的加载器可以解决发现问题，但不能把两个已分别定义的同名接口合并为同一类型。
