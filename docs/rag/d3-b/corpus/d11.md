# Redis RDB、AOF 与故障恢复

## 从恢复点看 RDB

Redis OSS 7.2 的 RDB 保存某个时点的数据快照。使用后台保存时，子进程写入快照，父进程继续接受请求，保存成功后替换旧文件。若最近可用快照对应 09:00，实例 09:03 故障，且没有可用于恢复的更新日志，重启加载该快照后，期间的修改可能丢失。快照通常便于保存和直接加载，生成过程仍受 fork、写时复制及磁盘资源约束。计划容许丢失多少数据，应从快照周期、保存耗时与故障假设推导，不能只看配置里的秒数。

## 从日志结构看 AOF

AOF 保存写入效果，重启时恢复基础状态并按顺序应用增量。Redis 7.0 起支持多段 AOF，Redis 7.2 可由 manifest 指定 base 与增量文件的组合。base 可采用 RDB 或 AOF 表达，重写会根据当前状态构建更紧凑的基础文件，同时处理并发产生的增量，目的是限制长期保留的写历史体积。不要在重写期间随意抽取个别文件拼成备份。AOF 的 `appendfsync everysec` 周期刷盘，常见丢失窗口约为一秒量级，遇到 I/O 卡顿和不同故障模型时无法作为严格上界。更频繁的 `always` 一般用更多 I/O 或延迟换更短的窗口。

## 把丢失容忍和恢复时长测出来

可从主库重建的缓存，可能选择重建或用 RDB 加快回暖。重建困难的业务状态需要更短的数据丢失容忍，可能需要 AOF 加独立备份，并评估是否应使用其他权威存储。RDB 一般直接加载快照；AOF 的恢复时间与 base、增量大小、重写状态、机器和 I/O 有关。对同一规模数据分别从快照与完整 AOF 文件集启动隔离实例，记录可读时点、最近可见业务状态和恢复后关键计数，以验证恢复点目标（RPO，允许丢失多少数据）和恢复时间目标（RTO，允许多久恢复服务）。

## 用独立故障域覆盖本机失效

本机持久化文件和实例可能共用磁盘；误删还可能被正常写入日志或进入新快照。保留独立位置的多个恢复点，按官方建议取得一致的快照或完整 AOF 文件集，核对摘要，并实际在隔离环境恢复。恢复要验证关键数据和业务约束，文件存在或服务能够启动都不足以证明可完整恢复。
