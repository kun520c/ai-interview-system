# MySQL EXPLAIN 和查询代价诊断

## 读传统计划

MySQL 8.0 传统 EXPLAIN 展示优化器选择的计划及估计。某表显示 `possible_keys=ix_customer, key=NULL, type=ALL`，意味着 ix_customer 是候选，本计划未选择索引，访问方式为全表扫描。高比例记录需要读取或随机回表代价高时，全扫描可能合理。若 `rows=100000, filtered=3.5`，估计本步检查十万行，其中约 3500 行通过本表的条件，`filtered` 单位是百分比。在连接中还需结合前序输入，不能把本表的估算通过行数直接当成整个查询结果数。 `Using where` 表示存在用于筛选行的 WHERE 条件。

## 检查哪些工作发生在取行之前

若复合索引有列无法用作连续范围定位，仍可能参与剩余过滤。例如索引 `(office, role, last_seen)` 的查询仅等值限制 office，再给出 last_seen 的范围。可以用 office 定位；如果计划和列条件适合索引条件下推，存储引擎先检查索引上的 last_seen，再为幸存项读取完整行。 `Using index condition` 反映这种下推，`Using index` 通常表示能从索引提供所需数据。 `Using filesort` 提示还要执行排序，输出本身无法确定排序有多少发生在磁盘上。

## 比较估计和真正执行

从 MySQL 8.0.18 开始，`EXPLAIN ANALYZE SELECT ...` 会执行查询并按迭代器给出实际时间、行数和循环次数。循环超过一次时，应留意单次平均值和总工作量；父子节点耗时可能重叠在同一执行路径内，不能把所有节点的数字相加来求总时长。它消耗真实 CPU、I/O 和连接资源，较重语句应先在隔离且具有代表性的数据上验证。普通 EXPLAIN 的 rows 与 filtered 依旧只是估计，查询跑完才能获得实际观测。

## 用参数分布定位原因

同一仓库中某状态占 90%，另一状态只占 0.1%，不要只拿少数值证明索引改进了全部查询。先用实际参数查看估计与测量偏差，再查统计是否漂移、谓词是否包住索引列而改变可用访问路径，或复合索引顺序是否适配查询。统计有问题时评估 `ANALYZE TABLE` 的效果和锁影响；匹配有问题时可以改写谓词或重新设计索引。对照组保持相近数据、参数、缓存和并发条件，比较扫描量和耗时，而非只数计划里出现了几个索引。
