# Redis 租约锁、所有权与故障边界

## 一次获取同时设置租期

以 Redis OSS 7.2 单实例为基线，为每次获取生成独立、难碰撞的随机 token，执行 `SET lock:asset:27 token NX PX 3000`。NX 只在键不存在时设置，PX 为新值同时设置毫秒租期。使用 SETNX 和单独的过期命令时，客户端在两步之间故障会留下没有期限的锁。收到成功回复才按已取得处理，获取超时则保留结果不明的分支，不能假定可以进入临界区。租期应根据业务耗时、等待预算和故障模型选择。

## 原子核验所有权后释放

A 的租期到期，B 可能接着取得同一 key。A 无条件 DEL 会删除 B 的租约；即使先 GET 再 DEL，过期与重新获取仍可以发生在两条命令之间。Redis 7.2 可用短 Lua 脚本在同一次服务器执行中比较 `redis.call('GET', KEYS[1]) == ARGV[1]`，相等才 DEL，否则返回零。有限续租也应在同一脚本中核验当前 token 后再 PEXPIRE，且设置最长持有时间和失败后的业务行为。Lua 在单实例内避免其他命令插入脚本执行步骤，仍要限制脚本工作量。

## 过期后旧执行者可能迟到

持有者 A 遇到长暂停，恢复时租约已归 B。随机所有者 token 能保护锁键释放，业务资源若不校验新旧写入资格，A 仍可能覆盖 B 的结果。若采用 fencing token，每次成功授权需获得与授权顺序一致的单调编号，接收方原子记录已接纳的最高编号并拒绝更旧的写入；只有 Redis 中增加编号而资源端不校验并无保护。也可直接以数据库条件更新、唯一约束或版本比较保护关键不变量。续租可以减少正常超期，不能代替接收端处理迟到写。

## 故障与热点回源

如果主实例确认获取后、复制之前故障，提升的异步副本可能没有该租约并允许另一个客户端获取。网络分区和停顿也会产生结果不明、暂时不可用或越过租期的执行。若租约仅用于合并热点缓存回源，可在获得资格后再查一次缓存，其他请求限时等候或在受限并发内降级，并将偶发重复回源纳入预算。若它保护支付或库存，仍须由权威存储确保最终不变量。测试可让 A 人为越过租期，观察其解锁返回零以及资源端拒绝旧写入是否各自成立。
