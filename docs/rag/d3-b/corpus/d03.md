# InnoDB 普通索引页、聚簇与二级访问

## 页组织与访问路径

MySQL 8.0 的 InnoDB 普通索引用 B-tree 组织，记录有序存放在叶页，可用 B+ 树类结构帮助理解。内部页用键范围导航到子页，一个页可以索引多个子页。对同样规模的平衡结构，较高扇出通常缩短根到叶的路径，有利于按页读写和缓存。等值查询先导航到目标位置，范围查询可定位下界后沿有序叶页扫描到上界。传统哈希索引适合等值查找，缺少直接有序扫描能力。InnoDB 的全文倒排索引及空间索引有不同结构，不能用普通 B-tree 模型概括。

## 聚簇与二级索引

每个 InnoDB 表有一个聚簇索引，其叶页中的记录承载行数据。优先选显式 PRIMARY KEY，无主键时尝试首个所有键列均非空的 UNIQUE 索引，仍找不到时用内部生成的聚簇键。聚簇记录保存行数据，长可变列能否全部内联还取决于行格式和长度。二级索引叶记录包含该索引的列以及用于定位聚簇记录的主键值。查询需要额外字段时，可先定位二级索引，再按该主键取聚簇记录，这次访问常称为回表。较宽主键会放大多个二级索引的条目体积，其影响要与定位策略和真实负载一起考虑。

## 覆盖按某次查询判断

假设仓储包裹表以 `id` 为主键，二级索引为 `(warehouse_id, arrived_at)`，有额外的 `raw_event` 字段。按仓库与到达时间范围只取 `id, arrived_at`，谓词和投影所需列可以由二级索引提供，包括隐含主键。此时查询可以覆盖，通常省去为获取这些列而访问完整行的步骤。加入 `raw_event` 后，该索引不再提供全部所需列，走此路径一般需要回表。覆盖描述查询所需列是否齐全。InnoDB 的 MVCC 可见性检查遇到某些近期更新或删除标记时，仍可能访问聚簇记录并读取历史版本。

## 观察而非猜测磁盘访问

在测试库装入可比的冷、热数据，分别 EXPLAIN 两个查询，核对所选 key 和 `Using index`。二级索引选中并不代表覆盖，覆盖也不直接说明物理 I/O 次数。选择性很低时，优化器可能选择成本更低的其他路径。若将长字段追加到索引以求覆盖，要比较读取收益、写入维护成本、页密度与存储体积。
