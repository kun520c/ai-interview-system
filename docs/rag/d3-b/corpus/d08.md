# 数据库并发扣减与持久化幂等

## 把库存条件放进权威写入

假设 MySQL 8.0 的一条 InnoDB 行保存展馆剩余预约名额，`slot_id` 唯一，`qty` 是校验过的正整数。可执行 `UPDATE slot_quota SET available = available - :qty WHERE slot_id = :id AND available >= :qty`。影响一行表示这次扣减完成，零行则按场景区分不存在或余量不足。正数和唯一定位是这段判断的前提。先普通 SELECT 后无条件更新会让多个请求基于同一个旧值决策。也可在同一事务内用 `SELECT ... FOR UPDATE` 锁行、检查再写，或把旧 version 放入更新条件并处理版本冲突。采用版本检查时，仍需依据读取到的余量判断并保证扣减条件在其版本前提下成立。

## 让并发重放得到已提交结果

给一次预约生成稳定请求 ID，重试保留 ID 和载荷。用非空唯一约束例如 `(account_id, operation, request_id)` 竞争受理资格，并持久化载荷标识、状态和结果。首次执行时，幂等记录、库存变动、预约记录和可供重放的结果处于同一 InnoDB 事务，全部提交或全部回滚。并发副本遇到重复键时不继续扣减，应结束本次事务，再按既定隔离语义查主库中已提交的受理记录。如果请求键相同、业务参数不同，返回合同约定的冲突。若原事务回滚，后来者只有在自身取得受理资格后才可以重新执行。跨服务通知等外部效果需独立的可靠发送及接收幂等合同。

## 超时后的恢复

能证实某次尝试从未发送时，服务端不会执行该次尝试。已发送后等待响应超时，或 COMMIT 发出后断连，客户端无法仅凭异常断定是否扣减成功。可按同一作用域的键查询持久结果，或提交同键同载荷请求让唯一约束重新裁定。查询暂时没看见记录并不能证明另一事务已结束。对死锁、锁等待超时等已分类的瞬态失败，先确认本次事务完整结束，再按有限次数、总时限和退避计划开启新事务。若默认只发生语句回滚，先结束整笔事务。需要在事务外调试异常时也保留稳定业务键。

## 可以怎样观察

在测试库给一个活动设五个名额。用两个连接各扣三席，检查剩余量、影响行数和事务结束时的预约记录。另开两次相同请求，其中一次在持久提交后模拟响应丢失，核对响应重放是否返回原预约以及数据库是否仅扣一次。再用同键改为两席，预期走载荷冲突分支。此类对照能独立发现「库存没负数但同请求扣两次」的漏洞。
