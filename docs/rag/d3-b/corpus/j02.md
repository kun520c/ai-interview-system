# 异常传播、资源所有权与抑制异常

适用 Java SE 21 的异常检查、控制流与 AutoCloseable 契约。

## 受检异常与失败边界

异常可沿调用栈传播到第一个匹配的处理器。编译器对可能逃出方法的受检异常要求捕获或在方法的 throws 声明中给出相容类型。例如文件读取的 IOException 可由调用者恢复，就在导入方法声明 throws IOException；非法参数 IllegalArgumentException 属于 RuntimeException，编译器允许省略捕获和声明，它仍可在运行时传播和被捕获。仅当处理器能恢复、向调用方明确返回失败或转换领域语义时捕获。将读取失败包装为 ImportException 时传入原异常作为 cause，方便区分文件不存在和其他 I/O 故障；返回空结果会使真实空文件与失败混淆。

## 成功取得资源与关闭顺序

使用 try-with-resources 约定自己打开的 AutoCloseable 文件流的生命周期。资源按声明顺序初始化，按相反顺序尝试关闭成功取得且非 null 的资源，正常完成、return 或抛出时均适用。已有 final 或有效 final 变量可放入资源列表。若先打开文件流 A、再打开输出流 B，且 B 初始化抛出，A 仍会关闭；若两个都成功取得，则先尝试 B.close，再尝试 A.close，即使 B.close 抛异常。由外部传入的共享流应先明确所有权，避免提前关闭其他调用者仍在使用的资源。

## 主异常、抑制异常与 finally

若导入正文抛出 readFailure，而 B.close 与 A.close 分别抛出 closeB 与 closeA，向外传播的是 readFailure，通常可按 B、A 顺序从 readFailure.getSuppressed() 读取清理失败。若正文正常而 B.close 先抛出，则 closeB 成为主异常，closeA 被附在其 suppressed 列表。cause 表示因果包装，由构造器或 initCause 设置；抑制异常表示同一退出过程中的其他失败。普通 finally 若直接抛清理异常，会以自己的异常退出原因替代原业务异常。示例以正常启用抑制且各异常实例独立为前提。
