# 线程池容量、拒绝与任务上下文

适用 Java SE 21 ThreadPoolExecutor 和复用的平台线程。

## 提交顺序和队列容量

运行中的 ThreadPoolExecutor 提交时，工作线程不足 corePoolSize 会先尝试创建核心工作线程；达到 core 后先尝试入队。入队后会复核运行状态，必要时移除并拒绝；若无工作线程也会尝试启动。无法入队时才尝试加线程至 maximumPoolSize，达到上限或池关闭走拒绝策略。无界队列通常让非核心扩容路径不起作用，堆上积压会拉长排队时间。设计应结合 CPU 或阻塞比例、连接池及下游允许并发，并以允许排队时间和对象内存共同约束队列容量。

## 任务受理和反馈

不能丢的任务需要明确受理边界，例如有持久待办记录，或在拒绝时明确失败并允许调用方幂等重试。CallerRunsPolicy 在未关停时用提交线程执行，能减慢生产者，但关停时可丢弃；在不宜阻塞的事件线程上也可能放大故障。Discard 与 DiscardOldest 不适合静默丢弃已确认任务。观察活跃线程估算、队列深度、拒绝率、排队和执行时延，分别用代表性的突发与慢下游验证参数。单靠线程数不能推断承载能力。

## 复用线程的上下文所有权

ThreadLocal 按线程保存值。请求 A 未清理，复用同一线程的请求 B 若在设置自身值前读取，会看到 A 的上下文；残留引用还可能让 A 的对象随工作线程继续被持有。由任务拥有的上下文应在任务边界 set，在 finally remove，嵌套场景则恢复先前值。异步传递可用显式参数，或在提交时仅捕获必要值，在执行线程安装后清除或恢复。InheritableThreadLocal 在线程创建时取初值，既有工作线程接到新任务时不会重新继承。
