# HTTP 方法、状态码与可重试合同

以 IETF RFC 9110 为准。查询既有任务的表示用 `GET /tasks/{id}`，成功通常为 200。由服务端处理载荷并分配新资源标识的创建可用 `POST /tasks`，成功创建可返回 201 并通过 `Location` 指明资源。`PUT /tasks/{id}` 表达在指定 URI 创建或替换状态。请求格式错误常用 400，目标资源不存在常用 404，未预料的服务端异常可用 500。安全性看客户端请求的预期操作，GET 可有正常日志等附带动作。幂等性看重复同一请求的预期服务端效果。GET、PUT 在规范中是幂等方法，响应可能不同，例如首次 PUT 为 201，随后更新返回 200 或 204。POST 没有通用幂等保证。

## 请求是否发送与提交是否发生

对某一次直接连接，若可证明未建立连接且未发送请求，则该次尝试没有抵达应用。Java HTTP Client 的 `HttpConnectTimeoutException` 表示连接建立超时，实际重试判断仍应考虑代理、连接复用和其他尝试。若已发送请求却未收到响应，无法仅凭客户端超时推断数据库是否提交。例如预约 POST 已创建记录而响应丢失，直接重放可能再次创建。客户端可在可核实的临时失败下重试符合语义的 GET、PUT。创建 POST 需要双方约定同一业务操作复用稳定幂等键与相同载荷，或改用等价的唯一资源标识和写入合同。

## 去重、重放与恢复预算

服务端可以用数据库唯一约束将幂等键、载荷语义和业务效果一并提交，并在重复请求时读取已有结果。同键异意图应被拒绝，且双方需约定键的保留期和进行中状态。重试只处理已识别的临时故障，使用整体期限、有限次数、退避和抖动，有适用的 `Retry-After` 时同时遵守它与本次总预算。鉴权失败、稳定的输入错误或明确的业务拒绝通常应先修正原因。测试时可让服务端成功提交后故意丢弃响应，断言复用原键仅产生一次创建效果。
