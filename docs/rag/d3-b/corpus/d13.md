# Cache-aside 的陈旧回填与热点保护

## 读 miss 与写后失效

在 MySQL 为权威来源、Redis OSS 7.2 作可丢弃读缓存的场景，应用先读缓存，miss 时读数据库，再按业务条件带 TTL 回填。写路径先提交权威数据，再删除缓存键，避免数据库仍旧时主动制造 miss。数据库写失败时不能把计划中的新值当成已提交结果。缓存失效命令失败应可观察，并依据业务容忍度重试或进入持久待办恢复。缓存提前淘汰也属于正常 miss；排查时比较过期和淘汰统计以及主动删除日志。

## 用时间轴看陈旧回填

读者 R 缓存 miss，从数据库拿到档案版本 41，暂时停在回填前。写者 W 提交版本 42，再删除缓存。R 继续执行，将 41 写回了已经清空的缓存。此时后续请求可能读到旧值，即使 W 完全按「提交后删除」顺序操作。TTL 可以约束这次回填后的保留时间，但仍要考虑超时请求、重复迟到回填及失效重试延误。严格读新值的路径可直接读主库，并明确事务快照、并发提交等读一致性边界。

## 版本条件与窗口

若读缓存的延迟收益重要，可让权威对象版本随写入单调递增，并在缓存保存最高已知版本的标记。缓存侧原子比较回填版本与标记及现有值，拒绝已过时的回填。删除数据时还需保留有效标记；标记被淘汰、过期或恢复丢失后，比较失去依据。从数据库提交到 Redis 发布新版本标记之间仍有窗口，发布丢失也要由可靠失效和恢复方案处理。选择有限陈旧策略时，应明确 TTL、允许延迟、最大加载时间及回退条件。可以在回填前加测试屏障，先让 W 提交并失效，再释放 R，检查是否重现旧回填以及保护条件是否生效。

## 热点 miss 与并发预算

热门档案同时失效时，可让同键请求合并到一个加载者。拿到回源资格的请求应重查缓存，再决定是否访问主库，其他请求带上限地等待或走降级路径。进程内 single-flight 只能合并该进程请求；多个实例可考虑跨实例协调，或用连接池配额、回源限流、快速失败及可接受的旧值降级限制总压力。Redis 故障时租约本身也可能不可用，数据库仍需要并发保护。合并用于减少回源，版本判断用于保护值的新旧，二者需要分别验证。
