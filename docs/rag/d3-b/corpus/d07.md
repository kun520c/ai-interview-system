# InnoDB 死锁、锁等待超时与恢复

## 等待成环与单向等待

在 MySQL 8.0 InnoDB 中，两笔转账分别先锁账户 5 和账户 9，再尝试取对方账户的锁，会形成循环等待。死锁检测开启时，引擎选择一个事务作为牺牲者并回滚其整个事务，客户端常见错误 1213。另一个场景是一笔事务已修改账户 5，等待被长事务锁住的账户 9，后者并不等待前者。这种单向等待也可能达到锁等待上限。默认 `innodb_rollback_on_timeout=OFF` 时，锁等待超时只回滚失败语句，通常报错 1205。账户 5 上的前序修改可能仍在当前未提交事务中，业务应显式结束并回滚，避免提交半笔转账。启用整事务超时回滚或关闭死锁检测时，诊断应按实际配置。

## 重新开始事务的边界

把可重试错误的识别、次数上限和退避放在事务外层。确认上一事务结束后，再新开事务执行完整的工作单元，回滚范围要核对引擎语义与框架异常规则。吞掉等待超时再继续 COMMIT 可能留下部分结果。在 COMMIT 发出后断连，客户端可能只知道结果未知。用稳定业务请求号、载荷校验和持久唯一约束，从主库确认已有结果或进入同键安全重试，避免再次扣款。遇到参数错误或业务拒绝等确定性失败时，应直接结束。给整个重试链设总时限，并为退避加入抖动可减轻并发放大。

## 降低等待与找到当时证据

如果每次都按账户 ID 升序锁定两行，题设的反向锁顺序循环可被打断。也可缩短事务，排除远端调用，改善索引定位以减少扫描和锁范围。依然要为其他写路径的死锁保留处理。 `SHOW ENGINE INNODB STATUS` 的最近死锁信息适合事后看涉及语句和锁，采集应及时，后来事件可能覆盖它。 `performance_schema.data_lock_waits` 联合 `data_locks` 可找采样时正在等谁及锁对象，采样时等待已经解除就可能没有行。可以用测试库的两个连接以相反顺序访问，再做单边长持锁对照，分别观测错误、整事务或单语句结果以及锁报告。
