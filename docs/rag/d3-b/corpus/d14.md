# Redis Pipeline、WATCH 事务与 Lua

## 独立操作采用批量往返

在 Redis OSS 7.2 单实例中，Pipeline 允许客户端先连续发送多条命令，再按顺序读取结果，减少网络往返。独立读取不同计数器是适用场景。Pipeline 本身没有命令组隔离保证，其他客户端的命令可交错执行，因此不能用一组 GET、判断、SET 来保护共享配额。应控制批量大小，服务端需要缓存尚未读走的回复；仍要检查每项回复。若多键读取恰好符合 MGET 的语义，也可以采用该单命令。

## WATCH 乐观流程与 EXEC 的两类错误

在同一连接执行 WATCH 配额键，GET 后判断余额，满足时 MULTI 排队更新，再 EXEC。观察期间键被修改、过期或淘汰时，Redis 7.2 的 EXEC 放弃这批命令，客户端根据空回复进行有限重试或返回冲突。连接复用前应释放 WATCH 状态。MULTI 队列阶段遇到未知命令或参数个数错误会让 EXEC 拒绝整个队列。已经合法排队的命令也可能在 EXEC 执行时碰到类型错误，此时对应位置返回错误，其他命令继续执行，之前成功的写入保留。测试时可先合法 SET 一键，再对一个已有 String 执行 LPUSH，检查 EXEC 的第二项错误以及第一项写入。

## 短脚本在一个执行边界内完成检查

单键配额也可用短 Lua 脚本先读取、校验，再在满足条件时扣减。执行期间其他客户端命令不能插入脚本步骤，但 Redis 服务端需要运行它，避免无界循环和大集合处理。把数据类型、参数范围、键状态及可能的业务拒绝尽量在写前验证，减少写后出错。在 Redis 7.2，若脚本已执行 SET，随后 `redis.call` 执行错误类型操作导致脚本中断，先前 SET 仍生效。 `redis.pcall` 可把命令错误作为值交给脚本处理，也不会撤销已成功动作。有写入效果后，SCRIPT KILL 不能用来杀掉并回滚该脚本。

## 如何选取和验证

互不依赖的读重在往返时间，适合 Pipeline。需围绕读取结果做条件更新时，可采用 WATCH 和有限冲突重试，也可在单实例用短脚本减少往返。用两个连接在 WATCH 和 EXEC 之间插入更新，验证队列被放弃；另将运行时类型错误放在一次成功写入之后，分别验证事务和脚本的保留效果。示例限定 Redis 单实例。涉及集群跨槽或外部存储时应另行定义约束。
