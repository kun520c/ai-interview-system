# TCP 与 UDP 的传输语义和 TCP 连接生命周期

以 IETF RFC 9293、RFC 768、RFC 5681、RFC 8085 为基线。TCP 为两个端点提供面向连接、可靠、有序的字节流。发送方利用序号和 ACK 跟踪已收到的字节，对丢失数据进行重传，应用需自行定义消息边界。UDP 按数据报保留消息边界，无 TCP 式握手；UDP 自身不保证送达、去重或顺序。TCP 的接收窗口约束发送方给接收端带来的缓存压力，拥塞窗口则约束向网络注入的在途数据，两者都限制发送量。序号、窗口与重传等状态通常也带来比 UDP 更高的协议维护开销。低时延媒体若能容忍部分过时帧丢失，可在 UDP 之上设计恢复和拥塞控制。需要完整顺序传输的文件可使用 TCP 并在应用层验证格式和完整性。

## 三次握手如何建立状态

常见主动建立过程是 A 发 `SYN(seq=x)`，B 回 `SYN(seq=y)+ACK(x+1)`，A 再回 `ACK(y+1)`。双方交换并确认各自初始序号，B 在收到对自己 SYN 的有效确认后完成该方向的同步。SYN 占用一个序号，SYN 与 ACK 可以在同一段。第三步还帮助区分当前建立与网络里延迟到达的旧 SYN；收到旧请求时，接收者不应仅凭一个 SYN 就把连接当作双方已建立。重传和同时打开会改变实际抓到的报文形态。

## 半关闭与两种常见关闭状态

TCP 全双工，两个发送方向可分别结束。A 发 FIN 并由 B 确认后，A 结束自己的发送方向但仍可接收 B 的数据。B 应用随后结束发送，B 发 FIN，A 再确认，这是常见的四报文时序，FIN 和 ACK 可以合并。普通主动关闭端进入 `TIME-WAIT`，协议以 2MSL 表达等待要求，用于在对端重发 FIN 时再次确认并让旧连接段过期。具体观察时长应查系统实现。`CLOSE-WAIT` 表示本地 TCP 已收到对端 FIN，仍在等待本地应用关闭。大量长期 `CLOSE-WAIT` 宜查应用资源释放，大量 `TIME-WAIT` 则结合主动关闭率、连接复用和端口压力分析。
