# TLS 1.3 服务器认证、密钥协商与用户身份

以 RFC 8446 的完整服务器证书握手为例，使用临时 (EC)DHE，排除 PSK、恢复、0-RTT 与双向认证。客户端需要分别验证证书链信任和服务身份。链验证根据受信任锚、签名、有效期和证书约束验证路径，服务身份检查则把应用预期连接的主机名与证书 SAN 中适用的 DNS 标识比较。给 `files.example.com` 签发的受信证书，如果不匹配 `api.example.com`，不应被后者的客户端接受。服务器的 `CertificateVerify` 用证书对应私钥签署握手 transcript 相关数据，证明持有私钥并绑定本次握手。

## 从临时密钥份额派生流量密钥

ClientHello 和 ServerHello 携带协商的公开密钥份额。双方各用自己的临时私有值和对端公开份额计算同一个 (EC)DHE 共享秘密。TLS 1.3 以 HKDF 密钥调度结合握手 transcript 派生握手及应用流量秘密，再导出各方向对称保护所需的密钥和 IV。共享秘密及流量密钥不需要明文发送。`Finished` 以握手派生密钥对 transcript 进行认证，验证对端确实掌握相应握手秘密并检查完整性。后续记录层使用 AEAD，为应用数据提供机密性及完整性保护。

## 传输认证与应用授权分层

普通服务器认证的 TLS 连接建立后，应用仍需决定请求用户是谁、能访问哪些资源。可使用会话 Cookie 或 Bearer 令牌承载应用凭证，由服务验证后按资源归属授权。无令牌收到 HTTP 401，与证书路径或主机名验证失败导致 TLS 握手不成立，发生在不同阶段。排查时可以分别观察有效链但名称不匹配、握手成功但未登录、以及两端无法协商密钥组这三种情况。
