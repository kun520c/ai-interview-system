## 2. 实际并发和流量模型

### 2.1 “两个消费者”的确切含义

**CONFIRMED。**最终 HTTP 实验运行一个 B 应用进程、一个 `DefaultMQPushConsumer` 实例；Broker 原日志显示测试 Topic 的读/写队列均为 1，消费组为 CLUSTERING。源码以 `MessageListenerConcurrently` 消费，`consumeThreadMin=consumeThreadMax=2`，每次拉取/回调消息批量为 1，队列拉取阈值为 8。回调内同步执行 CAS、模型请求和最终业务事务，返回后才 ACK。因此这里的 2 是**该实例的消费监听/业务执行线程数**，不是两个实例、两个 Topic 队列或全局模型调用许可；一个队列分配给一个同组实例并不阻止该实例并发处理多条消息。多实例和不同队列配置的总并发不能直接套用本结论。Broker 创建 Topic 和组心跳的原日志摘录见 `mq-control-evidence.txt`。

`report.async.consumer-threads` 默认 2，校验范围 1～8；此上限是配置允许值，不是历史流量实际并发的测量。本项目未配置全局模型 semaphore；DeepSeek 适配器使用 JDK HTTP Client，连接超时 3 秒、读取超时 60 秒；未在项目源码中设置专属模型执行器或每主机连接上限，不代表 JDK 内部连接无限或历史没有等待。历史启动脚本去掉 `SPRING_` 环境变量，两个 JAR 未打包 test profile；依打包配置和 HikariCP 6.3.3 默认值推断每应用连接池上限 10，历史没有 JMX/完整环境快照，不能作为当时实测上限。Tomcat 文档默认最大工作线程 200，但未保存全部 `SERVER_TOMCAT_*` 环境，不能认定当时的真实配置；采样非空闲线程 A/B 最大为 10/3。

### 2.2 由原始区间确定在途峰值

历史桩调用没有记录并发计数器；下面是有条件、可复算的**区间约束测量**，不是直接计数日志。每个请求对应一次至少睡眠 1000 ms 的本地桩调用。在一个必然包含该调用的区间 `[s,e]` 内，桩调用必然覆盖 `[e−1000 ms, s+1000 ms]`。A 使用客户端 POST 起止包住同步模型调用；B 使用同一 MySQL 时钟下的领取 `started_at` 和成功后的审计 `updated_at` 包住模型调用。假设时钟在相应一秒内没有跳变、实验源码/JAR 与清单一致，且该组无其他未记录模型调用。

- A：并发 10 两个波次的前十个独立 POST，这些必经区间分别共同重叠 **871.214 ms、962.734 ms**，所以至少 10 次桩调用同时在途；驱动最多 10 个虚拟用户，因此该实验观测峰值为 **10**。
- B：两个波次各找到一对必经区间，分别共同重叠约 **975.099 ms、972.329 ms**；单实例两条消费线程给出上限 2，因此该实验观测峰值为 **2**。样本 task/session 及时间见 `analysis-complete.json` 和脚本，`updated_at` 可能被迟到的投递确认延长，延长区间只会使该下界推导更保守。
- 并发 1 时，虚拟用户等 READY 才开始下一任务，桩记录每任务一次，故两版模型调用最多且实际均为 **1**。这提供已有的、同实际并发的单客户端机制对照。

高并发两波各 15 条，A 每波约 2.07 秒，B 约 10.11/10.05 秒；B 每次模型服务约 1 秒而一次最多执行两条，符合排队饱和现象。不能仅凭队列数推断模型调用串行，也不能把全部差距归因 RocketMQ 本身。历史 Casebook 使用的“两个消费者”应理解为此处的**两条线程**，不是实例数。

### 2.3 流量、资源与可比性

**CONFIRMED。**原驱动每个虚拟用户请求后要等待当前报告 READY 才循环下一条；B 使用 200 ms GET 轮询，等待计入闭环迭代。完成吞吐=两波客户端发现 READY 的成功数 ÷ 两波各自墙钟耗时之和，不是数据库完成时间上的吞吐，不是开放流量下的受理能力。受理吞吐同样受闭环下一轮到达时机影响。浏览器另用当前 Vue 前端，3 秒轮询，独立样本不与 HTTP 请求配对。

原 fixture 为每个任务建立独立用户、Session、回答与评价；同一组共用的题目仅被读取。B 的 297 个 HTTP 合成任务对应 297 个不同用户，弱项唯一键包含 `user_id`，因此本实验并发任务不争用同一用户弱项行。数据库页锁、索引、连接池、其他 SQL 锁及自增锁是否有争用没有历史等待指标，不能排除。297 对用户消息 Prompt 哈希一致，但不是整个模型 HTTP 请求、运行并发或流量形态一致的证明；A/B 原有 Session 背景分别 619/633。

原环境 Java 21.0.13、Docker 29.9.2，A/B 均 `-Xms128m -Xmx512m`，两台隔离 MySQL 各 1 CPU/768 MiB，同一本机模型桩；应用 JVM 无记录的单独 CPU 上限，且 A/B JVM 与 B Broker/NameServer 同时存在。机器并未清空其他服务，初始 load average 2.57/2.08/1.99。不能假定全部后台负载相同或将进程差值当成严格因果成本。HTTP 原实验 UTC `2026-11-14 17:02:59.823871`～`17:22:28.626001`；浏览器另测 `17:24:21.308883`～`17:49:40.849562`。

维持原 A10/B2 产品对照。现有配置校验上限为 8，无法只改 B 配置构造与 A 实测峰值 10 相同的 C，因此本轮没有声称完成 C，也没有单独限制 A 制造优势。若未来确需高于 1 的机制对照，可另设**两边相同任务数和实测并发上限**的 A/B/C 合成试验，并直接记录桩在途计数；例如各自投放 8 条、客户端最多 10，在两侧均实际达到 8 后才可称同并发，需另保留原 A10/B2 结果。8 线程只作为隔离桩候选，不是收费模型生产建议。

## 4. 恢复契约、锁和内容质量

### 4.1 模型返回后崩溃

[M1-A §8.2](2026-11-14-M1A-ROCKETMQ-ASYNC-REPORT-DESIGN.md)明确：RUNNING 消费者崩溃后扫描到执行期限，原 task 受控 FAILED，用户显式新请求生成新 task；该策略避免 MQ 重投自行反复付费。**CONFIRMED｜设计与实现一致；独立的用户产品批准记录未找到。**不能将其称作“任务永久丢失”，也不能称作“自动有限重试直至 READY”。DB 或扫描器停机时无法保证准时收口。

原故障 task 821 在模型替身返回后、完成事务前杀死进程：Session `GENERATING`、task `RUNNING/PENDING`、发送计数 0、报告 0、弱项 0；该探针直接发 MQ，故此处 PENDING 不是线上派发状态的代表。重复消息在 DB 可判定仍 RUNNING 时领取 CAS 不成功并 ACK，不再自动调用模型；测试配置期限 5 秒，并**显式调用** `expireTask`，而非证明生产 600 秒自然调度。此后旧 task 为 `FAILED/EXECUTION_EXPIRED`，显式新请求完成为 READY/SUCCEEDED；两次桩调用、报告 1、弱项 1。新 task 不复用旧 task/版本。旧 task 的 `attempt_version`、执行 CAS 的 `execution_version` 为不同阶段的身份防护；旧执行者即使晚返回，也不得覆盖新的报告或新任务状态。模型结果未持久化，重试可能再次付费；“模型再次调用”和“报告/弱项重复提交”是两个不同问题。

后续策略须作明确选择，本轮均未改变：

1. **维持人工重试**：对外准确声明等待执行期限、失败提示、人工重试及可能再次调用，保留可观测和失败告警。优点是当前成本边界明确；缺点是需要人工介入，无法承诺自动 READY。
2. **有界自动恢复**：仅在明确产品需求后，基于现有 task、期限和版本设计持久可审计的重试次数/费用预算，进程重启不重置预算，旧执行者仍经 CAS fencing，处理提交结果未知和重复投递。现有 `attempt_version` 是会话版本，不能直接当独立重试计数；现有字段是否足够尚未证明，若需要 DDL 须按项目规则另行分析批准。增加外部调用及成本，不引入第二套调度平台或无限重试。

### 4.2 归属锁与一级缓存

当前源码顺序是普通 `getReportOwnerId` 预查所有权 → `getReportVersionForUpdate` 锁行 → `getReportSession` 查询完整记录并再次检查所有权/状态 → 最终 CAS；无权用户不必先等待其他人的行锁，合法竞争仍受行锁和版本串行化。该事务服务已声明 `READ_COMMITTED`；现有入口没有包围它的外层业务事务，在此隔离级别下锁后的独立 SELECT 能读取等待期间已提交的归属变化。锁前/锁后不同 MappedStatement ID 会进入 MyBatis 3.5.19 一级缓存 key；本路径加锁前没有调用后者，因此锁后读取不会复用锁前 owner 查询的结果。不同 ID 解决的是缓存键问题，不能脱离事务隔离级别单独保证数据库视图新鲜。`useCache=false` 控制二级缓存路径，**不等于关闭一级缓存**；这一判断同时核对了依赖源码与真实 MySQL 测试。原始失败保留：先锁后鉴权 `1/0/1/0`，第一次相同查询造成归属变化误接收 `1/1/0/0`；最终相关定向 `75/0/0/0`，旧执行者四交错 `4/0/0/0`。这些是历史结果，不是本轮新测试。

源码与事务测试显示该生成路径在事务外调用模型；派发器无包围 MQ send 的外层业务事务，领取和记账分开。既有 [ReportDatabaseFixture](../../src/test/java/com/kun/aiinterview/interview/service/ReportDatabaseFixture.java) 对生成器事务状态有断言。B 在受理、执行前及完成前有多次 FINAL/资格检查，当前没有足够逐阶段证据计算其代价；不得为性能删除权限、FINAL、幂等或旧执行者校验，也不需要全局禁用缓存、改隔离级别。

### 4.3 真实模型内容独立问题

原两次真实报告的合成 FINAL 输入均 `strengths=[]`、`missing_points=[]`、`correction=null`，模型输出却作出关于 HashMap 细节欠缺的具体判断；Prompt 发送题目快照及评价而非原答，现有结构校验不能证明文本有依据。两次结果证明存在样本级无证据判断，不能估计总体错误率。[输入及输出证据](m1c-20261114/real-report-evidence.json)仍在；本轮未修改 Prompt、评分 v4、题库或 RAG。两次外部模型测试运行的是较早 JAR `cf1a199e...`，**最终 B JAR 未做真实模型验证**。

## 5. 最多三项最小后续修改建议

以下均为候选，**本轮没有实施**；收益均为待验证假设：

1. **补最小观测，先验证原因。**在隔离测试注入逐任务扫描开始/租约领取/发送确认/回调/CAS/模型起止/事务提交/首次 GET；进程内用 monotonic，跨进程记录校准后的 UTC 及误差，按 task/version 关联，直接记录桩在途及池/锁等待，禁止记录凭据和内容。风险是测量扰动和日志量；用原数据作基线，检查是否改变事务/ACK 与实际耗时。
2. **只在隔离桩下验证更短调度。**优先通过现有 `scan-interval-ms` 配置比较；如确有必要再评估事务提交后本地唤醒并保留定时补扫。假设是减少低负载领取等待；代价可能是更高数据库扫描 QPS、本地唤醒在提交后崩溃时丢失及定时竞争。必须保留 Outbox、发送租约、双重 CAS，验证崩溃后补扫并测 DB CPU/连接数、每任务开始到完成与轮询误差；不承诺已获得收益。
3. **只在隔离桩下调节有界消费并发。**在保留原 A/B 下，测 2 与不超过现有上限的候选值，并用相同真实在途并发、相同任务量补充机制对照。假设是减少高负载积压；代价可能是模型同时付费、DB 池/锁争用、期限压力和 Broker 重平衡。应记录实际在途、排队、池等待、CPU/RSS、失败和重复写，保留旧执行者及故障测试；不把隔离值直接推荐给收费生产模型。

浏览器 3 秒轮询也是可测的交互选择；本轮证据尚不足决定修改间隔。恢复策略和 137 运维处置分别按第 4、6 节决策，不为凑性能数字改变一致性约束。
