## I01｜并发完成后请求重放错误

- **面试官可能问：**你的答题接口如何实现幂等？如果并发请求已经成功，为什么还可能返回 500？
- **60 秒口述：**项目以请求身份和载荷识别重复提交。历史并发测试发现，A 先读到旧答案，B 完成评价并推进会话后，A 又读取了新会话，因当前题不一致误报 500。修复保留权限和载荷校验，在发现当前题已变化时重新读取答案；如果已持久化为 EVALUATED，就复用评价和最新会话响应。历史隔离 MySQL 和模型替身的确定性交错测试覆盖了该场景，但不代表模型调用全局恰好一次。
- **2～3 分钟展开：**先说明会话、答案、requestId 和状态：同一用户重发同一载荷应得到已保存结果，不同用户或内容不能借用结果。原链路在首读 Answer 与再读 Session 之间存在并发窗口：另一个请求可能已经完成写入并切题，旧快照会让校验把成功误判为内部错误。唯一索引或 CAS 能限制并发写胜者，却无法让两次读天然处于同一业务时点。修复先处理 EVALUATED 的显式重放，在当前题不符时重新读取并确认已完成，仍对无评价的异常状态报错。历史测试使用两处暂停点和五种推进路径，改前 16/10/0/0，后续业务定向 286/0/0/0；模型是替身，不能扩大为全网证明。收尾解释实际贡献，以及自己能否画出交错和条件。
- **深度追问：**requestId 与 attemptId 有什么不同？为何不能见到重复键就无条件返回 200？结果已保存但状态错误如何处理？
- **真实取舍：**两次有条件只读校验比全局锁和长事务简单；保留真正不一致异常。
- **证据：**[H01](PROJECT_ENGINEERING_HISTORY_20261111_20261115.md#h01)、[B1 原验收](../verification/B1_CONCURRENT_IDEMPOTENT_REPLAY_20261111.md)、[并发测试](../../src/test/java/com/kun/aiinterview/interview/service/InterviewConcurrentReplayIntegrationTest.java)。
- **不能宣称：**所有竞态已穷尽、无重复外部调用、上线生产流量验证。
- **需学习：**Workflow.evaluateAnswer、requireReloadedAnswer，InterviewService.submitAnswer；学习路线 03。

## I02｜领取成功后的异常收口与外部调用边界

- **面试官可能问：**任务已被领取，后续查询或模型调用失败时怎么恢复？
- **60 秒口述：**项目把请求身份和执行 attempt 分开。一次评价短事务先领取并记录 attemptId，随后在事务外准备上下文和调用模型；历史故障注入发现领取之后、模型之前的下一题查询在 try 外，出错就漏掉 FAILED 收口。修复把这段查询纳入已有保护范围，失败时用同一 attempt 条件更新，避免旧执行者覆盖新状态。若数据库不可写或进程硬退出，仍需要超时与恢复机制，不能声称每次都立即恢复。
- **2～3 分钟展开：**重放请求用于找到同一个业务提交，attemptId 用于指明本轮执行者。领取成功即数据库已经提交 EVALUATING，并不等于业务完成。如果下一步查询失败而异常处理范围没覆盖，后续重放只能看到执行中，直到 stale 恢复。曾考虑扩大事务，但把数据库锁覆盖外部网络调用会增加等待，且不能让外部模型结果与 MySQL 原子提交。最终只在确认拥有执行权之后，用同一 attempt 写 FAILED，若失败回写也异常则保留原始异常并附加诊断。历史改前 44/7/0/0、修复后 44/0/0/0，独立连接确认提交；注入的是查询异常，不是真实数据库断网。进一步说明模型超时后服务商是否完成和计费未知，不能盲目无限重试。
- **深度追问：**失败回写失败怎么办？事务传播是什么？服务端超时是否意味着供应商停止计算？
- **真实取舍：**短事务加执行权条件保护可避免旧执行者覆盖；代价是要另处理进程退出和不可写数据库。
- **证据：**[B2 原验收](../verification/B2_POST_CLAIM_FAILURE_RECOVERY_20261111.md)、[DeepSeek 超时验收](../verification/B4C_DEEPSEEK_TIMEOUT_RETRY_20261112.md)。
- **不能宣称：**所有错误自动立即恢复、模型超时绝不收费或重复。
- **需学习：**Workflow.claimOrRecoverEvaluation/markEvaluationFailed、事务 Service 和 Answer Mapper；学习路线 04、05、11。

## I03｜FINAL 一致性与报告事务

- **面试官可能问：**一场面试有追问时，你如何避免重复计算分数和弱项？
- **60 秒口述：**项目一题最多一次追问：无追问时主答评价直接 FINAL；有追问时主答 INITIAL，追答后的综合评价才是 FINAL。报告不能只检查评价数量，因为可能存在重复 MAIN、错绑答案或追问。历史修复让 SQL 不再用 INITIAL 兜底或隐藏重复，Java 再校验 MAIN 集合、答案和追问归属；最终报告、弱项与 READY 放在事务里。已 READY 历史报告保持可读，没有偷偷重算。
- **2～3 分钟展开：**说明为什么“一题一条 FINAL”是集合约束而非 COUNT 约束。假设计划五题，第一题有两条 FINAL、第二题缺失，数量仍是五，直接按条数平均会混入错误。旧 SQL 的 INITIAL 兜底和排名过滤会掩盖这类异常。修复后保留重复记录给 Java 检查，核对计划顺序、主问题身份、最终答案及追问关联；弱项服务拒绝非 FINAL。首轮修复后又发现已有报告、状态尚未 READY 的恢复分支没有复用检查，因此再次堵住旁路。历史扩展 134/0/0/0、普通全量 1589/0/0/19，另有 24 项真实 MySQL、模型替身；结构正确不代表模型评价的技术事实一定正确。当前未提交异步版本把相同聚合职责放进 FinalReader，版本边界需要说清。
- **深度追问：**历史 READY 异常报告是否修复？已有报告如何避免重复更新弱项？事务在哪一步开始？
- **真实取舍：**不自动清洗历史数据；恢复路径共享不变量，代价是可能拒绝需要人工核对的历史异常。
- **证据：**[B3 验收](../verification/B3_REPORT_FINAL_CONSISTENCY_20261111.md)、[FINAL 集成测试](../../src/test/java/com/kun/aiinterview/interview/service/InterviewReportFinalConsistencyIntegrationTest.java)。
- **不能宣称：**历史数据已全面清理，或最终评价语义已准确。
- **需学习：**FinalReader.aggregateFinalEvaluations、AnswerEvaluationMapper.xml、UserWeaknessService、报告事务；学习路线 02、12。

## I04｜MySQL 行锁与 MyBatis 一级缓存的连环问题

- **面试官可能问：**有没有一次修复并发问题时，第一次修复仍然失败？
- **60 秒口述：**报告受理最初先锁 Session 再检查归属，真实 MySQL 测试中无权请求会等待别人的行锁。第一次修复在锁前后读取同一查询，但锁等待期间模拟归属变化，MyBatis 一级缓存可能复用锁前结果。最终方案先独立普通查询 owner，无权即拒绝；有权者锁行，再通过不同 Mapper 语句读完整 Session 并复核。历史真实 MySQL 两个关键并发用例及相关定向验证通过，这不等于曾证明发生数据泄露。
- **2～3 分钟展开：**先把锁范围讲清：基于主键的 FOR UPDATE 针对该 Session 行，非所有者本来就不应为了得到 404 等待目标用户的事务。预查可以减少无权等待，但不能作为唯一授权，因为从预查到锁之间存在 TOCTOU；锁取得后还要再验 owner。首修使用相同 Mapper 查询做两次读取，在同一事务的 SqlSession 中可能命中一级缓存，于是模拟 owner 改变的测试暴露旧值。最终 getReportOwnerId 和 getReportSession 是不同语句，锁后重新读取；报告事务 READ_COMMITTED，且持锁核验。历史首修前 1/0/1/0、首修 1/1/0/0，最终相关定向 75/0/0/0。不能只说 useCache=false 就关闭一级缓存，也不能把模拟 owner 变化说成线上存在转让功能。
- **深度追问：**为什么预查不能防 TOCTOU？不同 SQL 和隔离级别分别承担什么？当前读/快照读如何区别？
- **真实取舍：**增加一次普通查询换取非所有者早拒绝，同时保留锁内复核；不全局关闭缓存。
- **证据：**[M1-C 故障记录](2026-11-15-M1C-FAILURE-INJECTION.md)、[真实 MySQL 用例](../../src/test/java/com/kun/aiinterview/interview/service/ReportOwnershipLockIsolationTest.java)。
- **不能宣称：**已发生实际越权泄露、全局缓存问题已消除或完成恶意高并发安全测试。
- **需学习：**acceptReportTask、getReportOwnerId/getReportVersionForUpdate/getReportSession；学习路线 06。

## I05｜RocketMQ 与 Transactional Outbox 的分工

- **面试官可能问：**为什么引入 MQ？数据库写成功后再发消息不就行了吗？
- **60 秒口述：**报告原来同步等待模型，项目研究持久异步受理。先写 DB 再发 MQ 有提交后进程退出导致未发送的窗口，先发再写又可能消费到回滚任务。方案把 Session 状态和任务记录放在一个 MySQL 事务，任务表兼 Outbox；派发器按租约扫描并发普通消息，消费者再依据数据库 CAS 领取。数据库事务不包含 Broker 和模型，消息可重复；另有纯数据库 Worker 方案，组件更少，项目选择 MQ 是权衡而非性能必需。
- **2～3 分钟展开：**以用户点击生成为例说明 POST 返回 GENERATING，持久 task 与 Session 同事务提交。Dispatcher 查到 PENDING 后用条件更新取得租约，事务外发送，确认后按 dispatchToken 记 SENT；若发送成功却没记账，租约到期可重发同一标识。消费侧不能相信消息携带的身份来授予业务写权，要再锁 Session 和 Task、校验 attempt/version、CAS 成功后才调用模型。普通消息加 Outbox 保留可恢复记录，代价是扫描、存储、死信和运维；事务消息虽然能用半消息与本地回查协调，仍需稳定事务结果和消费幂等，本轮没有同时叠加。M1-B 的隔离真实 MQ+MySQL 测试使用模型替身；不能说实现了跨数据库与 MQ 的原子事务，也不能说已生产部署。
- **深度追问：**markSent 晚于消费者完成时会怎样？MQ 事务消息为什么仍需要幂等？为什么不用数据库 Worker？
- **真实取舍：**一个任务表兼 Outbox，避免重复实体，同时为投递和执行维护两套状态。
- **证据：**[M1-A 设计](2026-11-14-M1A-ROCKETMQ-ASYNC-REPORT-DESIGN.md)、[M1-B 验收](2026-11-14-M1B-ROCKETMQ-ASYNC-REPORT-VERIFICATION.md)、[任务 SQL](../../src/main/resources/mapper/InterviewReportTaskMapper.xml)。
- **不能宣称：**零丢消息、分布式原子事务、仅靠 MQ 即保证业务恰好一次。
- **需学习：**acceptReportTask、dispatchDue、claimDispatch、markSent、onMessage；学习路线 08、09。

## I06｜重复消费、执行围栏与崩溃恢复

- **面试官可能问：**重复消息或消费者崩溃会不会重复生成报告？
- **60 秒口述：**消费时数据库以任务状态和版本 CAS 选出一个执行者，并固定 executionVersion。最终事务再次检查身份、状态和 deadline，才写报告、弱项、READY 与任务成功；旧执行者超时后不能借新版本覆盖。历史故障注入显示，业务提交后 ACK 前退出，重投不会再调用模型；但模型返回后、数据库提交前退出，任务超期 FAILED，用户重试可能再次调用模型。因此能讨论数据库提交幂等，不能承诺模型调用恰好一次。
- **2～3 分钟展开：**区分投递身份、申请 attempt 和执行 version：前者防迟到发送回执覆盖租约，后两者防重复领取和旧执行者提交。消费者领取后模型在事务外；成功时最终事务再次读取 FINAL 与 session/task，并检查 version 和期限，然后原子写四类结果。如果业务已成功而 ACK 未返回，重投看到已终态，不应再调生成器；如果模型已返回但应用在提交前死掉，系统并不知道外部服务结果是否可靠保存，因此旧任务到期后 FAILED，由用户显式新请求申请，模型可能第二次计费。历史在专用 MySQL/MQ 与替身模型下做过进程杀死、重复投递和四种旧执行者交错；测试有缩短 deadline 和手动触发，不是自然长超时或所有生产灾难场景。死信只是消息状态，业务失败仍要数据库收口。
- **深度追问：**RUNNING 重投是否立即再次执行？用户未重试时会自动 READY 吗？DB 提交结果未知时应如何 ACK？
- **真实取舍：**宁可明确 FAILED 等用户重试，也不无界重复收费；仍需告知体验与恢复代价。
- **证据：**[故障矩阵](2026-11-15-M1C-FAILURE-INJECTION.md)、[崩溃探针](../../src/test/java/com/kun/aiinterview/interview/service/RealReportCrashWindowProbeTest.java)。
- **不能宣称：**模型 exactly once、所有崩溃自动成功、自然长超时或 MySQL 真停机均已验证。
- **需学习：**claimTaskExecution、completeReportGeneration、expireTask、finishSuccess；学习路线 10–12。

## I07｜异步化后的性能退化与指标口径

- **面试官可能问：**引入 RocketMQ 后性能提升了多少？
- **60 秒口述：**历史实验反而发现完整报告退化。固定一秒模型桩、并发 10、每组 30 条，异步 POST P95 为 24.9 ms，同步是 1046.5 ms，但前者只表示受理，后者已经完成。客户端看到 READY 的 P95 同步/异步为 1046.5/6967.8 ms，闭环完成吞吐为 7.252/1.489 次每秒。异步增加了扫描、排队及有限消费并发，这些都需分解；不能宣称模型加速或把小样本桩结果说成生产性能。
- **2～3 分钟展开：**先定义实验对象：同步版是 Git 基线，异步版是该基线加未提交 MQ 工作区的指定 JAR；固定一秒的模型替身，每组两轮 15 条、闭环并发 10。同步 POST 返回 READY，异步 POST 返回 GENERATING，再以 200 ms 查询；因此仅比较两个 POST P95 会把不同语义放一起。完整 READY 和客户端完成吞吐明显变差，后续 R1 依据时间区间保守推导同步模型请求可重叠 10 个、异步单实例执行线程 2 个；并发 1 时仍有约 874 ms 入队到领取中位等待，包含扫描、Broker 和调度，不能全归于扫描。R2 才在新协议中直接埋点并做线程、扫描对照。开放式到达测试与闭环完成吞吐不同，少量样本 P95 不等于容量规划。主动说明背景数据库行数、资源和整个请求体可比性有限。
- **深度追问：**P95 如何算？为什么客户端轮询影响观察时间？闭环和开放式到达如何改变吞吐解释？
- **真实取舍：**MQ 用于持久受理与受控消费，不默认当作生成加速工具。
- **证据：**[M1-C 原始 A/B](m1c-20261115-after-fix/AB_RESULTS.md)、[R1 归因](M1C_R1_BOTTLENECK_REVIEW.md)。
- **不能宣称：**异步报告完整生成提升 97%、线上 QPS 或真实 DeepSeek 吞吐达到桩结果。
- **需学习：**A/B 脚本、原始请求、分位数与调用链；学习路线 14。

## I08｜有界并发、扫描调优与提交后唤醒

- **面试官可能问：**已经发现异步变慢后，你如何选择优化点？
- **60 秒口述：**历史 R2 先用直接计时和模型桩在途计数分解等待，再将消费线程 2 调到 4、扫描周期 2000 调到 500 ms；在同一 20 条闭环小样本中，客户端完成速率 1.775→3.531 次每秒，READY P95 6067.4→3563.6 ms，仍不能证明优于同步。随后 M1-E 在数据库提交后增加有界唤醒提示，周期扫描仍兜底；它改善单并发桩等待，但真实完整报告耗时没有证明稳定下降。
- **2～3 分钟展开：**线程增加可以让等待外部 I/O 时有更多任务在途，但受服务商并发、连接池、CPU 和数据库限制；扫描更频繁可减少等待下一轮的延迟，却增加 DB 查询。R2 先逐项对照，再只调整默认 2→4 和 2000→500 ms，没有移除 FINAL 校验、CAS 或权限检查。原 30 条实验与 R2 的 20 条协议不能混算，调优后仍慢于同步基线。M1-E 选择在事务提交后发布可丢失提示：独立一线程容量一、合并提示，调用原派发器并继续依赖租约 CAS，拒绝时已接受任务仍由定时扫描发现。单并发固定 1 秒桩各 8 条，持久流水线中位 1.463→1.040 秒；并发 8 的样本没有改善。12 次真实调用中 11 READY、1 FAILED，配对成功样本波动明显，因此不能承诺完整 AI 报告稳定加速。
- **深度追问：**扫描器不能运行时怎么办？AFTER_COMMIT 为什么还需要有界线程池？多线程为什么不能无限提高吞吐？
- **真实取舍：**少量可回退配置与可丢失提示，保留扫描和一致性；代价是更高查询频率与模型并发。

## I09｜AI 评分质量、人工盲审与 RAG 证据

- **面试官可能问：**模型能返回合法 JSON，是不是说明评价可靠？你如何评价 RAG 的效果？
- **60 秒口述：**结构校验只能保证字段、范围和评分点 ID 合法，不能证明技术事实或证据支持判断。项目风险挑选 12 张卡，用户先做总体盲看，后续工程复核有 7 张至少一项可确认输出问题，但不能据此推断总体错误率。实例包括 LEFT JOIN 主方案正确而额外 WHERE 写法丢行、已答 removeIf 被判遗漏。Q2 v5 在 18 次真实调用中 17 次通过解析与 Java 校验，仍有漏判和退化，故撤回、保留 v4，评分内容仍 NO-GO。
- **2～3 分钟展开：**先解释数据契约：模型建议五维分数、每点 covered、证据和反馈，Java 验证结构后求和并用规则决定追问。当前 covered 是二值，无法区分部分和完全未答；true 必须有非空 evidence，但不自动证明该片段来自原答或支持结论。人工复核不能只看总分，要区分遗漏、额外技术错误、等价实现及题目没有要求的扩展。LEFT JOIN 用 MySQL 反例判断 WHERE 变体；接口 private 方法用 Java 8/9 编译反例核对。12 卡是风险分层样本、最初不是逐点 gold，因此 7/12 不是总体准确率。RAG 历史 63/63 Hit@1 与 75/315 直接相关证据说明命中不等于高精度；标签多由临时 AI 判断，还需独立人工金标准。Q2 v5 虽 18 次 HTTP 200、17 次结构通过，仍有错判和一次非法 JSON，于是撤回；后续七条规则候选因无有效模型对照未应用。

## I10｜响应丢失后的恢复、权限与渐进展示

- **面试官可能问：**报告或答案提交慢，如何让用户刷新后继续看结果，同时不泄露数据？
- **60 秒口述：**业务提交成功但响应可能丢失，项目从受所有权保护的详情重新读取已保存评价，避免重发答案和重复调用模型；详情只返回当前题与允许的已答历史，不返回未来题。异步报告生成中又复用已有 FINAL 结果提前展示，并明确综合报告尚未 READY。历史三对浏览器样本首次有用内容中位数 4.223→0.085 秒，但展示内容不同，不代表完整报告或模型生成提速。
- **2～3 分钟展开：**先说明 U2 的真实组合场景：服务端提交并进入下一题后响应丢失，旧页面依赖本机记录，重启或新浏览器无法恢复；因此从详情按顺序读取最近已评价题，而不是重发答案。安全方面，完整组卷快照存在数据库中并不意味客户端能看到未来题，S1 修复前五道题会一次返回，后来先校验归属并只返回当前题与已答历史。M1-E 的 P3 在报告 GENERATING 或 FAILED 时展示有权读取的已保存结果，不新建伪评价，也不修改 READY；完整 DeepSeek 报告仍需最后事务提交。收口又修复手动检查和定时轮询重叠：同一会话共享在途查询，用户或路由变化靠 epoch 隔离，离页停止新轮询。历史真实浏览器三对是小样本；完整报告页有变慢和失败样本。最新收口前端 349/0/0/0，后端全量 1947/0/0/34 为前次结果复用，不应混称本次重跑。
- **深度追问：**如何防止切换账号后展示上一用户结果？旧请求是否真正取消？提前显示是否意味着报告 READY？
- **真实取舍：**复用持久化详情减少重复调用和等待，但增加前端状态协调；提前展示内容与最终综合报告必须区分。
- **证据：**[S1 验收](../verification/S1_INTERVIEW_VISIBILITY_SECURITY_20261114.md)、[U2 报告](/Users/kun/Documents/Reports/ai-interview-system/2026-11-14-U2-恢复修复与运行安全验收.md)、[M1-E 收口](m1e-20261115/DECISION_AND_VERIFICATION.md)。
- **不能宣称：**0.085 秒生成 AI 报告、所有旧请求都被网络取消、评分质量已验收。
- **需学习：**InterviewService.getDetail、PreviousInterviewFeedback.vue、useInterviewReport、InterviewReportView；学习路线 01、13。
