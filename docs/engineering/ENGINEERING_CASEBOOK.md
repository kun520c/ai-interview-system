## M1-A：异步报告、可靠投递与有界恢复（2026-11-14）

- **状态：仅设计。** 同步报告的模型调用使 HTTP 等待外部服务；用户可以通过持久化任务、快速受理和状态查询在刷新后继续查看，队列也提供受控消费并发的可能。未测得吞吐或生成时间收益，单体数据库任务线程是更少组件的合理替代。
- **关键取舍：**单表任务兼 Outbox，Session 状态与待派发事件同一 MySQL 事务；发送结果不确定可重复投递，消费者再用执行领取与 version fencing 保护报告/Weakness 的唯一提交。对比普通发送的双写窗口与 RocketMQ 事务消息的半消息和回查复杂度，方案仍增加表、扫描器、Broker、重试、监控和迁移成本。
- **最重要的边界：**排队与执行使用不同 deadline；旧 `updated_at` stale 不能直接用于 MQ 排队。模型调用可能重复，DB/应用全停时不能保证按墙上时间变 FAILED；DB 恢复后由扫描器收口。尚无真实 MQ、故障注入、性能或实施证据，不能写成已上线。
- **证据及下一步：**[M1-A 方案](2026-11-14-M1A-ROCKETMQ-ASYNC-REPORT-DESIGN.md)、B3/B4-E 和 U1/U2 历史验收。Schema 冻结例外需在实施前对具体 DDL/迁移另获明确批准；[学习项](SOURCE_LEARNING_BACKLOG.md#l-m1a-01)待学习、掌握未确认。

### 全程复盘补充：从同步报告到持久任务

- **背景与现象：**原 `generateReport` 在 HTTP 请求内等待模型，再由短事务写入报告、弱项和 READY；已有版本 CAS、报告唯一约束和请求驱动的 stale 恢复，并非完全没有恢复。模型慢或连接中断时，客户端必须等待或重新查询，连接寿命与模型耗时耦合；这不是当时已证明吞吐不足。
- **方案和选择：**讨论原同步、MySQL 持久任务＋本地有界执行器、普通消息＋同库 Outbox，以及 RocketMQ 事务消息；选择单体中的任务表兼 Outbox 和普通消息。Session 改 GENERATING 与任务 PENDING 在同一 MySQL 事务，发送在事务外；队列与执行分别设期限。避免把旧版 `updated_at` 的 stale 规则直接套在可能长时间排队的新任务上。[原设计](2026-11-14-M1A-ROCKETMQ-ASYNC-REPORT-DESIGN.md) · [H13](PROJECT_ENGINEERING_HISTORY_20261111_20261115.md#h13)
- **取舍／状态：**单表避免重复业务任务和事件实体，但增加投递、执行两套进度以及扫描、重投和监控。普通 DB 提交与 Broker 发送不构成原子事务；事务消息的半消息和回查也不能替代业务幂等。M1-A 的独立真实收发只证明基础连通，后续 M1-B 才实施并测试；任务表迁移须逐目标批准。
- **面试问题：为什么 MQ 而不是线程池？** 持久异步让请求释放，RocketMQ 提供独立消息存储和消费分发；裸内存线程池进程退出会丢待办。更公平的替代是**数据库持久任务＋有界本地执行器**，它也能提供持久受理和恢复，但本项目未实现或对照它，不能说 MQ 已被证明必需。学习入口 [L-M1A-01～04](SOURCE_LEARNING_BACKLOG.md#l-m1a-01)，掌握未确认。

## M1-B：提交权与投递进度分离的异步报告（2026-11-14）

- **问题与实现：**原 POST 同步等待模型；改为 Session CAS 与 Outbox 同事务受理，消息只含稳定 ID，消费 CAS 后才获得固定 executionVersion。模型在事务外，最后一笔事务一起写 Report、Weakness、READY 和 SUCCEEDED。两个消费者、晚到租约回执、超时旧执行者各由不同条件保护，不能只靠一条唯一约束。[源码、调用链与验收](2026-11-14-M1B-ROCKETMQ-ASYNC-REPORT-VERIFICATION.md)。
- **真实反例与修正：**消费者可能在生产者写 SENT 前完成，因此 markSent 只修改匹配 token 的投递字段。真实 Broker 重试入 DLQ 不会把 QUEUED 自动变 FAILED，受控重放先查 DB；第一次 CLI 探针把表格误当 MessageExt 导致 2 个超时错误，保留失败证据后修正。全量测试曾因多 Spring 上下文各建 10 连接耗尽 MySQL 151 连接上限，只限制测试池为 4/minIdle=0，保留原并发断言。
- **验证及限制：**最终后端 1923/0/0/23、前端 341/0/0/0；真实 MySQL 原子回滚、版本/租约竞争和真实 MQ 重复/停机/DLQ/重放已验证，模型替身。未实测杀应用进程、丢弃真实 ACK 或共享 MySQL 停机，不能写外部模型恰好一次、零丢消息或性能提升。javassist 旧 effective-model 告警仍记录为剩余兼容项。

### 全程复盘补充：两个进度、两个事务和实际失败

- **问题→方案：**先写 DB 后发送，提交后进程退出可能未发送；先发 MQ 后写 DB，消息可能先于回滚的任务被消费。`acceptReportTask` 在 Session 锁内 CAS 状态并插入 `QUEUED/PENDING`，两者同事务；`ReportOutboxDispatcher.dispatchDue` 用 token 和期限领取租约后，在事务外发送，仅按原 token 记 SENT。消息只含 taskId、sessionId、attemptVersion。[实现验收](2026-11-14-M1B-ROCKETMQ-ASYNC-REPORT-VERIFICATION.md) · [任务 SQL](../../src/main/resources/mapper/InterviewReportTaskMapper.xml)
- **发送结果不确定：**发送超时并不证明 Broker 未收到；已收到但进程在记 SENT 前退出，也可能在租约到期后重发。历史场景确实测试过 SEND_OK 后、记账前杀进程并重发；它不是对真实网络确认包丢失或数据库 `markSent` 提交失败的实测。后者由代码保留租约并等待恢复，是设计处理，不能写成已发生的真实故障。消费者甚至可能先完成，故迟到 `markSent` 只更新匹配租约的投递字段，不覆盖 SUCCEEDED。
- **多消费者→唯一业务提交：**回调内 `claimTaskExecution` 按 Session→Task 锁序检查 attempt、状态和期限，以 CAS 确定唯一执行者并固定 `executionVersion`；模型调用在事务外。`completeReportGeneration` 再验执行权、deadline 和 FINAL，报告、Weakness、Session READY、Task SUCCEEDED 同一事务提交；中间任何异常回滚。已有历史报告时不重放 Weakness，而是留审计告警。数据库任务表是权威业务状态，MQ 消息仅是投递线索；单靠消息去重或报告唯一索引无法保护所有副作用。
- **验证与失败尝试：**M1-B 真实 MySQL/MQ、模型替身验证重复投递和消费者先于 `markSent`；历史 DLQ 首轮探针因误读 CLI 输出 `2/0/2/0`，修复解析后 `2/0/0/0`；DB 不可读由 Mock 注入，不是真实 MySQL 停机。首轮全量 `1920/2/1/22` 暴露测试 stub 与多个测试连接池耗尽，修正测试并限制测试池后，最终 `1923/0/0/23`；失败记录未抹除。生产故障、测试工具故障与环境问题不能混写。
- **面试问题：为什么有 MQ 还要任务表，怎样避免重复报告/弱项？** MQ 不负责 session 的所有权、FINAL、状态和本地事务；用表保存任务、租约和期限，再由 CAS/固定版本及最终同库事务控制业务副作用。MQ 可重复投递，Java 不承诺模型调用恰好一次。关键入口：[事务服务](../../src/main/java/com/kun/aiinterview/interview/service/InterviewReportTransactionService.java)、[消费回调](../../src/main/java/com/kun/aiinterview/interview/report/async/ReportMessageConsumer.java)、[真实 MQ 测试](../../src/test/java/com/kun/aiinterview/interview/service/RealReportRocketMqSmokeTest.java)。个人掌握未确认。

## M1-C：真实崩溃窗口与 A/B 反例（2026-11-15）

- **动机和方案：**同步 POST 等待模型；M1-B 将 Session 与任务/Outbox 放进同一 MySQL 事务，Broker 通知后以 Session→Task 锁序、执行 version 和最终事务控制写入。选择单表是因为任务本身已在 MySQL，不需再维护第二个 Outbox 实体；代价是 Broker、定时扫描、消费限流、监控及切换排空。它不构成 DB 与 MQ 的分布式原子事务，也不保证外部模型恰好一次。
- **修复前历史实验：**独立 A/B、每组每配置 30 条，1 秒模型桩/并发 10 时 A/B POST P95 分别 1086.4/22.1 ms，但 A 返回 READY、B 仅受理；READY P95 为 1086.4/7089.4 ms，闭环完成吞吐为 7.206/1.476 次/秒。B 默认两个消费者，受扫描间隔、队列和额外一致性校验共同影响，不能只归因 MQ；不是生产容量。该结果对应所有权锁修复前 JAR，原始数据及九组结果见 [历史 A/B](m1c-20261114/AB_RESULTS.md)。
- **故障事实：**真实 MySQL+独立 RocketMQ、替身模型下，提交后 kill/停复 Broker 自动完成；SEND_OK 后 kill、重发两份及两个消费者竞争均只提交一个报告和一次弱项；DB 提交后 ACK 前 kill 的真实重投不再调用模型。模型返回后、提交前 kill 则超时失败，显式重试产生第二次模型调用；旧执行者四种交错由真实 MySQL 单独验证。[故障记录](2026-11-15-M1C-FAILURE-INJECTION.md)区分真实进程、测试替身及直接数据库期限注入。
- **真实模型与限制：**经单独批准使用 2 次 DeepSeek；两次结构、分数、报告和弱项持久化及浏览器轮询/刷新成立，但空优势/遗漏输入下出现无证据的具体欠缺描述，内容质量不能判通过。消费者死亡后无自动重新生成；纯 MQ 投递时间及供应商账单未获得。总体 **NO-GO**，不宣称性能普遍提升、生产高可用、模型恰好一次或语义正确。全量回归及运行边界见 [方案和环境](2026-11-15-M1C-TEST-PLAN-ENVIRONMENT.md)。
- **首轮状态：**B 和本轮文件均未提交、未推送；截至首轮修复仅限实验桩、时间口径、故障探针和导出编码。其后发现并修复所有权锁问题，最终代码的回归和性能须分别记录。学习项仍待开发者本人复现或讲解确认。

### 全程复盘补充：一次任务在不同崩溃窗口的去向

- **可复现证据：**历史修复后构建在独立真实 MySQL/MQ、模型替身下做五组进程窗口，5/5 达到各场景断言；杀死的测试进程退出非零不记作 JUnit 通过。只有第一组恢复阶段使用当时最终 JAR，其余由同源码测试进程和替身触发，不等于现合并 SHA 全矩阵实测。[原始故障窗口](2026-11-15-M1C-FAILURE-INJECTION.md)
- **实际处理：**DB 已提交、尚未发送时，重启后扫描持久待办，Broker 恢复后完成；SEND_OK、未记 SENT 时租约过期可重发；不同消费组制造的双消费者竞争仅一个执行者有效；业务提交后、消费回调 ACK 前退出，真实重投看到终态，第二进程不再调用模型。测试使用不同消费组制造重复，不是同组重平衡或跨机 HA 验证。
- **实验工具的失败与修正：**早期同步探针因模型桩只接受 Content-Length、不能解析 chunked 请求而得到 502；修桩后验证通过。将 UTC 与本地时间直接相减曾得到约 8 小时假耗时，随后统一时区；首次模型返回后崩溃探针因 Mockito spy 事务代理失败而未到故障窗口，改为真实事务 bean 加测试替身后重跑；CLI 导出中文曾变 `?`，以 utf8mb4 重导，错误原件保留。它们是实验设施或取证问题，不能当作生产缺陷或事后删除。[失败细目](2026-11-15-M1C-FAILURE-INJECTION.md#复现根因修复与尚未解决)
- **仍有限制：**模型返回后、最终事务前进程死亡，旧任务经测试缩短的执行期限变 FAILED，用户显式重试才有新 attempt；该例模型调用两次但报告、弱项各一次。旧执行者四种交错的真实 MySQL 测试 `4/0/0/0`，用注入期限而非自然等待，禁止旧版本覆盖新 attempt。真实模型返回后 kill、JDBC 提交未知、真实网络 ACK 丢失和 MySQL 真停机均未验证。
- **面试问题：为什么需要 CAS 和 executionVersion？** CAS 解决当前状态下谁能领取；固定 executionVersion 让旧执行者即使晚返回，也无法通过最后的所有权和期限检查。它约束数据库结果，不能撤销已发出的模型请求。开发者需自行学习后再用第一人称讲述。[L-M1C-02](SOURCE_LEARNING_BACKLOG.md#l-m1c-02)

### M1-C 补充：跨用户锁等待与 MyBatis 一级缓存

- 无权请求先锁他人 Session 导致在真实 MySQL 行锁上等待，修复前定向结果 `1/0/1/0`。第一次修复在锁前后复用同一查询，事务内 MyBatis 一级缓存使锁后读取可能重用旧结果；模拟锁等待期间归属改变时，旧所有者仍被接受，定向结果 `1/1/0/0`。这不是已证明的数据泄露，也未假设系统存在会话转让接口。
- 最终通过独立 Mapper 查询非锁定预读 owner，加锁后再以不同语句读取并重检，两个真实 MySQL 并发回归及相关测试共 `75/0/0/0`；最终普通后端全量 `1938/0/0/34`。最终修复源码的五组进程故障重跑均符合场景断言，其中场景 1 恢复时运行最终 JAR，其余窗口由 Surefire 测试进程和替身注入；模型返回后崩溃仍须显式重试。[故障记录](2026-11-15-M1C-FAILURE-INJECTION.md)。

#### 全程复盘补充：第一次修复为什么仍不安全

- **实际问题：**真实 MySQL 目标行被锁时，非所有者请求先等锁再被拒绝；修复前 `1/0/1/0`。先做归属预查虽能减少无权等待，但锁前到锁后存在状态变化窗口，不能只信预查。
