## M1-A：异步报告、可靠投递与有界恢复（2026-11-14）

- **状态：仅设计。** 同步报告的模型调用使 HTTP 等待外部服务；用户可以通过持久化任务、快速受理和状态查询在刷新后继续查看，队列也提供受控消费并发的可能。未测得吞吐或生成时间收益，单体数据库任务线程是更少组件的合理替代。
- **关键取舍：**单表任务兼 Outbox，Session 状态与待派发事件同一 MySQL 事务；发送结果不确定可重复投递，消费者再用执行领取与 version fencing 保护报告/Weakness 的唯一提交。对比普通发送的双写窗口与 RocketMQ 事务消息的半消息和回查复杂度，方案仍增加表、扫描器、Broker、重试、监控和迁移成本。
- **最重要的边界：**排队与执行使用不同 deadline；旧 `updated_at` stale 不能直接用于 MQ 排队。模型调用可能重复，DB/应用全停时不能保证按墙上时间变 FAILED；DB 恢复后由扫描器收口。尚无真实 MQ、故障注入、性能或实施证据，不能写成已上线。
- **证据及下一步：**[M1-A 方案](2026-11-14-M1A-ROCKETMQ-ASYNC-REPORT-DESIGN.md)、B3/B4-E 和 U1/U2 历史验收。Schema 冻结例外需在实施前对具体 DDL/迁移另获明确批准；[学习项](SOURCE_LEARNING_BACKLOG.md#l-m1a-01)待学习、掌握未确认。

## M1-C：真实崩溃窗口与 A/B 反例（2026-11-15）

- **动机和方案：**同步 POST 等待模型；M1-B 将 Session 与任务/Outbox 放进同一 MySQL 事务，Broker 通知后以 Session→Task 锁序、执行 version 和最终事务控制写入。选择单表是因为任务本身已在 MySQL，不需再维护第二个 Outbox 实体；代价是 Broker、定时扫描、消费限流、监控及切换排空。它不构成 DB 与 MQ 的分布式原子事务，也不保证外部模型恰好一次。
- **修复前历史实验：**独立 A/B、每组每配置 30 条，1 秒模型桩/并发 10 时 A/B POST P95 分别 1086.4/22.1 ms，但 A 返回 READY、B 仅受理；READY P95 为 1086.4/7089.4 ms，闭环完成吞吐为 7.206/1.476 次/秒。B 默认两个消费者，受扫描间隔、队列和额外一致性校验共同影响，不能只归因 MQ；不是生产容量。该结果对应所有权锁修复前 JAR，原始数据及九组结果见 [历史 A/B](m1c-20261114/AB_RESULTS.md)。
- **故障事实：**真实 MySQL+独立 RocketMQ、替身模型下，提交后 kill/停复 Broker 自动完成；SEND_OK 后 kill、重发两份及两个消费者竞争均只提交一个报告和一次弱项；DB 提交后 ACK 前 kill 的真实重投不再调用模型。模型返回后、提交前 kill 则超时失败，显式重试产生第二次模型调用；旧执行者四种交错由真实 MySQL 单独验证。[故障记录](2026-11-15-M1C-FAILURE-INJECTION.md)区分真实进程、测试替身及直接数据库期限注入。
- **真实模型与限制：**经单独批准使用 2 次 DeepSeek；两次结构、分数、报告和弱项持久化及浏览器轮询/刷新成立，但空优势/遗漏输入下出现无证据的具体欠缺描述，内容质量不能判通过。消费者死亡后无自动重新生成；纯 MQ 投递时间及供应商账单未获得。总体 **NO-GO**，不宣称性能普遍提升、生产高可用、模型恰好一次或语义正确。全量回归及运行边界见 [方案和环境](2026-11-15-M1C-TEST-PLAN-ENVIRONMENT.md)。
- **首轮状态：**B 和本轮文件均未提交、未推送；截至首轮修复仅限实验桩、时间口径、故障探针和导出编码。其后发现并修复所有权锁问题，最终代码的回归和性能须分别记录。学习项仍待开发者本人复现或讲解确认。

### M1-C 补充：跨用户锁等待与 MyBatis 一级缓存

- 无权请求先锁他人 Session 导致在真实 MySQL 行锁上等待，修复前定向结果 `1/0/1/0`。第一次修复在锁前后复用同一查询，事务内 MyBatis 一级缓存使锁后读取可能重用旧结果；模拟锁等待期间归属改变时，旧所有者仍被接受，定向结果 `1/1/0/0`。这不是已证明的数据泄露，也未假设系统存在会话转让接口。
- 最终通过独立 Mapper 查询非锁定预读 owner，加锁后再以不同语句读取并重检，两个真实 MySQL 并发回归及相关测试共 `75/0/0/0`；最终普通后端全量 `1938/0/0/34`。最终修复源码的五组进程故障重跑均符合场景断言，其中场景 1 恢复时运行最终 JAR，其余窗口由 Surefire 测试进程和替身注入；模型返回后崩溃仍须显式重试。[故障记录](2026-11-15-M1C-FAILURE-INJECTION.md)。
- **最终构建对照：**1 秒模型桩、并发 10、每组 30 条，A/B POST P95 **1046.5/24.9 ms**（A 是完成、B 是受理）；申请至轮询观测 READY P95 **1046.5/6967.8 ms**，闭环完成吞吐 **7.252/1.489 次/秒**。九组中 B 完整 READY P95 均更高、完成吞吐均更低；默认两消费线程与派发/校验共同影响结果，不能归因单一因素。[最终 A/B](m1c-20261115-after-fix/AB_RESULTS.md)记录逐条数据、资源和背景数据库差异。真实 DeepSeek 的两次浏览器测试使用修复前构建，不能代表最终 JAR 已连接真实模型。
